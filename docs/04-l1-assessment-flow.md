# 04 — L1: Assessment Flow

**L1 covers everything from a job being posted to the aptitude and coding exam
results being available.** The interview is L2 and starts in
[05-l2-interview-flow.md](05-l2-interview-flow.md).

```
1. Job posted            admin
2. Candidate applies     resume + details
3. ATS screening         TF-IDF + skills + experience + education -> score
4. Shortlist             automatic (threshold) or manual
5. Candidate mails       acknowledgement / reconfirmation
6. Question paper        uploaded, or generated by gpt-4o from the JD
7. Assessment assigned   exam window, per-question timing, pass mark, mail
8. Pre-exam checks       desktop, camera, mic noise, identity photo, room scan
9. Aptitude exam         MCQ, proctored, timed
10. Coding exam          Monaco editor, run against test cases, proctored
11. Grading              percentage vs pass mark -> PASSED / FAILED
12. Results              admin table + candidate view + Excel / PDF export
                                                     <-- L1 ends
```

---

## 1. Job post

**Frontend** — [`JobPostFormPage`](../src/pages/admin/JobPostFormPage.tsx) serves
both create and edit (`/admin/jobs/create`, `/admin/jobs/:jobPrefix/edit`);
[`AdminJobsPage`](../src/pages/admin/AdminJobsPage.tsx) lists with
[`JobListControls`](../src/components/jobs/JobListControls.tsx) and
[`useJobListing`](../src/hooks/useJobListing.ts).
[`ShareJobLink`](../src/components/admin/ShareJobLink.tsx) produces the public
apply URL via `applyJobUrl(jobPrefix)`.

**Backend** — `JobPostController`:

| Endpoint | Permission |
| --- | --- |
| `POST /api/jobs/post` | `JOB_POST_CREATE` |
| `PUT /api/jobs/post/{id}` | `JOB_POST_UPDATE` |
| `DELETE /api/jobs/post/{id}` | `JOB_POST_DELETE` |
| `GET /api/jobs/getPost` | `JOB_POST_READ` |
| `GET /api/jobs/counts`, `GET /api/jobs/job-types` | `JOB_POST_READ` |

`jobPrefix` is the unique business key used everywhere downstream — assessments,
results, prompts and interviews are all keyed by it rather than by job id.
Deletes are soft (`deletedAt`, `deletedBy`); `JobPostSpecifications` builds the
filtered list queries.

## 2. Candidate applies

**Frontend** — [`JobApplicationPage`](../src/pages/candidate/JobApplicationPage.tsx)
works both from `/candidate/apply` and from the shareable
`/candidate/apply/:jobPrefix`, in which case the job is loaded from the URL.
[`ReferralFields`](../src/components/application/ReferralFields.tsx) collects an
optional referral. Resume validation uses `APP_CONFIG.SUPPORTED_RESUME_TYPES`
(PDF, DOC, DOCX) and a 2 MB cap.

**Backend** — `POST /api/job-applications/apply` (multipart, `JOB_APPLY`).
Creates a `JobApplicationForCandidate` with `status = APPLIED`, storing the
resume bytes in `resumeData` plus `resumeFileName`/`contentType`.
`PATCH /api/job-applications/update` amends an existing application.

Applications are read back with:

- `GET /api/job-applications/{email}` — the candidate's own
- `GET /api/job-applications/byJobPrefix/{jobPrefix}` — everyone on a job
- `GET /api/job-applications/byJobPrefixAndEmail/{jobPrefix}/{email}` — one row

## 3. ATS screening

**Frontend** — [`AtsScreeningPage`](../src/pages/admin/AtsScreeningPage.tsx) for
a single job's applicants, [`AtsBatchPage`](../src/pages/admin/AtsBatchPage.tsx)
for a folder of resumes screened against a JD.
[`AtsResultsTable`](../src/components/admin/AtsResultsTable.tsx) and
[`AtsCandidateDetailModal`](../src/components/admin/AtsCandidateDetailModal.tsx)
render the outcome; [`ScreeningRunReport`](../src/components/admin/ScreeningRunReport.tsx)
summarises a run.

**Backend** — two entry points:

| Endpoint | Use |
| --- | --- |
| `POST /api/job-applications/screen` | Screen a whole job, or only the emails passed in |
| `POST /api/upload-multiple-resumes` (`ATS_UPLOAD_MULTI`) | Batch-screen uploaded resumes against a JD |
| `POST /api/upload-single-resumes` | Single resume |

`ATSServiceImpl.screenResume` extracts text with Tika, extracts the candidate's
email with a regex, then scores. The score combines TF-IDF cosine similarity,
skill match (expanded through `synonyms.json`), experience-years match and
education match, clamped to 0–100 and written to `matchPercent`. The pass line
is `ats.screening.threshold` (default `60.0`).

> `GET /api/job-applications/filterByPrefix/{jobPrefix}` is **deprecated** — it
> re-screened the whole job on every GET. The client marks it as such and uses
> `SCREEN` instead.

## 4. Shortlisting

Automatic shortlisting follows from the ATS threshold. Manual shortlisting is
`PATCH /api/job-applications/shortlist` with `{ jobPrefix, emails, override }`,
which lets a recruiter push someone through regardless of score.

`PATCH /api/job-applications/referral-status` sets `PENDING`, `VERIFIED` or
`REJECTED` on a referral;
[`ReferralTag`](../src/components/admin/ReferralTag.tsx) renders it.

The pipeline itself is worked from
[`CandidateDetailsPage`](../src/pages/admin/CandidateDetailsPage.tsx) with
[`CandidateTable`](../src/components/admin/CandidateTable.tsx),
[`BulkActionModal`](../src/components/admin/BulkActionModal.tsx) for
multi-candidate actions, and
[`ResumeViewerModal`](../src/components/admin/ResumeViewerModal.tsx).

## 5. Candidate emails

Every mail is an admin-triggered POST under `/api/job-applications`, all
requiring `JOB_APPLICATION_READ_ALL`, each backed by a Thymeleaf template and an
`EmailType`:

| Endpoint | `EmailType` | Sent when |
| --- | --- | --- |
| `send-ack-mail` | `ACKNOWLEDGEMENT` | Application received / shortlisted |
| `send-reconfirmation-mail` | `RECONFIRMATION` | Candidate must confirm availability |
| `send-exam-link` | `EXAM_SCHEDULE` | Exam window is set |
| `send-success-mail` | `WRITTEN_TEST_SUCCESS` | Passed the exam |
| `send-failure-mail` | `WRITTEN_TEST_FAILURE` | Failed the exam |
| `send-rejection-mail` | `REJECTION` | Rejected at any point |

`GET /api/job-applications/acknowledge` is the candidate-side confirmation link
target. Sender name, company, portal URL, support address and test venue all
come from `app.mail.*` in `application.properties`, so branding changes in one
place rather than per template.

## 6. Question papers

Two routes into a paper:

**Uploaded** — [`UploadQuestionPaperPage`](../src/pages/admin/UploadQuestionPaperPage.tsx)
posts to `POST /api/upload` (`ASSESSMENT_UPLOAD`). The client parses it with
[`question-paper.utils.ts`](../src/utils/question-paper.utils.ts) to detect the
question count, which then prices the exam clock.

**Generated** — `QuestionController`:

| Endpoint | Permission | Produces |
| --- | --- | --- |
| `GET /api/generate-questions?jobPrefix=` | `QUESTION_GENERATE` | Aptitude MCQs |
| `GET /api/generate-coding-questions?jobPrefix=` | `CODING_QUESTION_GENERATE` | Coding problems with test cases |

Both call `OpenAiServiceImpl` with `gpt-4o`, steered by the job's stored prompt
(`JobPrompt`, `PromptType.APTITUDE` / `CODING`). The client allows
`AI_GENERATION_TIMEOUT_MS` = 330 s for these, since generation is slow.

Prompts are edited on [`JobPromptPage`](../src/pages/admin/JobPromptPage.tsx) via
`/api/prompts`.

## 7. Assigning an assessment

**Frontend** — [`AssignAssessmentPage`](../src/pages/admin/AssignAssessmentPage.tsx),
with [`ExamDurationFields`](../src/components/admin/ExamDurationFields.tsx) and
[`PassMarkField`](../src/components/admin/PassMarkField.tsx). The admin picks
candidates, the paper, the exam window, the per-question allowance and the pass
percentage.

**Backend** — `POST /api/assign` (`ASSESSMENT_ASSIGN`), or `/api/assign-blob`
when the paper is stored in object storage. One `Assessment` row is created per
candidate carrying:

`assessmentType`, `candidateEmail`, `jobPrefix`, `questionPaper`, `answerKey`,
`assignedAt`, `startTime`, `deadline`, `minutesPerQuestion`, `durationMinutes`,
`questionCount`, `estimatedDurationMinutes`, `passPercentage`,
`containerName`/`fileName`.

> `assignedAt` is when the admin assigned it; `startTime` is when the exam
> window opens. They are different fields and must not be conflated — see commit
> `4b63bd8`.

`assignAssessment` returns an `AssignmentReportDTO` naming anyone whose exam was
created but whose email failed, so the recruiter can resend. The client allows
`ASSIGN_TIMEOUT_MS` = 120 s for the call.

**Rescheduling** — `PATCH /api/assessments/{id}/schedule` moves the window of a
paper not yet sat, from
[`RescheduleExamModal`](../src/components/admin/RescheduleExamModal.tsx).
`notify` defaults to true server-side: the candidate was told the old window, so
a silent move would leave them turning up to an exam that has gone.

**Expiry** — a per-minute job bulk-updates rows past their deadline, and an
hourly job calls `expireAssessments()`.

## 8. Pre-exam checks

**Frontend** — [`ExamInstructionsPage`](../src/pages/candidate/ExamInstructionsPage.tsx)
gates entry to the exam. It runs, in order:

1. **Desktop check** — [`useIsDesktop`](../src/hooks/useIsDesktop.ts); phones are
   refused.
2. **Camera permission** — [`useExamCamera`](../src/hooks/useExamCamera.ts).
3. **Face presence** — [`useFaceDetection`](../src/hooks/useFaceDetection.ts) at
   a fast 1 s cadence here, with readings only trusted after two settling cycles.
4. **Mic noise** — [`useMicNoiseLevel`](../src/hooks/useMicNoiseLevel.ts) and
   [`NoiseLevelMeter`](../src/components/exam/NoiseLevelMeter.tsx): below
   `NOISE_WARN_DB` green, up to `NOISE_BLOCK_DB` amber, above it red once
   sustained for `NOISE_SUSTAIN_MS`. Red blocks the start only if
   `NOISE_BLOCKS_START` is on.
5. **Identity photo** — [`ExamIdentityCheck`](../src/components/exam/ExamIdentityCheck.tsx),
   downscaled to `PHOTO_MAX_WIDTH` and uploaded.
6. **Room scan** — optional 360° sweep capturing `ROOM_SCAN_FRAMES` frames over
   `ROOM_SCAN_DURATION_MS`.

Every step is switchable through `VITE_PROCTORING_*`
([`proctoring.config.ts`](../src/config/proctoring.config.ts)) so an environment
can loosen or tighten checks without a code change.

**Backend** — `ExamProctoringController`:

| Endpoint | Access |
| --- | --- |
| `POST /api/exam-proctoring/identity-photo` (multipart) | Candidate |
| `POST /api/exam-proctoring/room-scan` (multipart) | Candidate |
| `GET /api/exam-proctoring/assessments/{id}/captures` | `ASSESSMENT_READ` |
| `GET /api/exam-proctoring/captures` | `ASSESSMENT_READ` |
| `GET /api/exam-proctoring/captures/{captureId}/image` | `ASSESSMENT_READ` |

Captures become `ExamProctoringCapture` rows (`IDENTITY_PHOTO` or
`ROOM_SCAN_FRAME`) with the bytes in object storage and
`containerName`/`fileName` on the row. Admins view them through
[`ProctoringCaptures`](../src/components/admin/result/ProctoringCaptures.tsx).
Contract detail: [backend-requirements-exam-capture.md](backend-requirements-exam-capture.md).

## 9. Aptitude exam

[`AptitudeAssessmentPage`](../src/pages/candidate/AptitudeAssessmentPage.tsx),
rendered inside [`ExamLayout`](../src/components/layout/ExamLayout.tsx) — no
sidebar, no navbar.

**Load** — `GET /api/fetchAssessment/{id}` returns the paper; `normalizeQuestions`
handles both option shapes the backend emits (`{"A":"…","B":"…"}` and the legacy
array). `POST /api/markExamAttended` records the start.

**Clock** — `computeExamMinutes()` = question count × `minutesPerQuestion`
(default 1 for aptitude), with the assignment's override winning.
`EXAM_TIMER_MINUTES` = 120 is only a fallback for a paper whose count is unknown.

**Proctoring during the exam** — `useExamProctoring` enforces fullscreen, counts
tab switches and face warnings, and calls `onAutoSubmit(reason)` when a limit is
hit. `useBeforeUnload` warns on reload, because a reload restarts the paper with
a fresh clock.

**Submit** — manual, or automatic on timeout or violation. The page computes
`score`, `totalMarks` and `percentage = round(score / totalMarks * 100)`, then
`POST /api/result` (`ASSESSMENT_RESULT_SUBMIT`) with the answer JSON as body and
the rest as query params. `buildSubmissionMeta()` attaches a
`__submissionMeta` block recording `MANUAL` vs `AUTO`, the reason, the client
timestamp, seconds left and duration — which is how the result screens can later
say "auto-submitted, proctoring, 20 min left".

> The percentage is sent explicitly because raw marks are not a percentage.
> Grading raw marks against a pass percentage failed papers that had actually
> passed.

## 10. Coding exam

[`CodingAssessmentPage`](../src/pages/candidate/CodingAssessmentPage.tsx) — the
largest screen in the app (~1400 lines), same `ExamLayout` lockdown.

- **Editor** — Monaco, language chosen from `APP_CONFIG.COMPILER_LANGUAGES`
  (Java, Python, C, C++, JavaScript).
- **Clock** — 25 minutes per question by default.
- **Run** — `POST /api/compiler/run` (`COMPILER_RUN`). The server compiles once
  and runs every test case, returning a per-case `ExecutionStatus` (`PASSED`,
  `WRONG_ANSWER`, `COMPILE_ERROR`, `RUNTIME_ERROR`, `TIMEOUT`,
  `OUTPUT_LIMIT_EXCEEDED`, `NOT_RUN`, `INTERNAL_ERROR`). Client timeout 120 s,
  above the server's 45 s bound so typed errors survive.
- **Test-case visibility** — `VITE_CODING_TESTCASE_VISIBILITY`: `locked`
  (nothing shown until a case passes), `open` (everything shown), or `partial`
  (first N open, rest unlock as they pass). See
  [`coding-exam.config.ts`](../src/config/coding-exam.config.ts) and
  [`TestCaseCard`](../src/components/admin/result/TestCaseCard.tsx).
- **Unattempted** — `POST /api/compiler/save-unattempted` records questions the
  candidate never ran, so a blank is distinguishable from a failed attempt.
  [`isSkeletonCode`](../src/utils/code.utils.ts) tells an untouched template from
  a real attempt.
- **Submit** — same path as aptitude: `POST /api/result` with submission
  metadata attached.

Submissions persist as `CodeSubmission` (script, language, `questionId`,
`answersJson`, `attempted`, `passed`) with a `TestResultEntity` per case
(input, expected, actual, status, error, `executionTimeMs`).

## 11. Grading

- Aptitude: correct answers vs answer key, converted to a percentage on the
  client and re-checked server-side.
- Coding: test cases passed, banded by the paper's difficulty labels.
- Verdict: `percentage >= assessment.passPercentage` → `ResultStatus.PASSED`,
  else `FAILED`. Default pass mark is on the `Assessment` row
  (`DEFAULT_PASS_PERCENTAGE`), overridable per assignment.

A `Result` row stores `score`, `totalMarks`, `percentage`, `status`,
`submittedAt`, the full `resultsJson`, and links to the assessment, candidate and
job.

## 12. Results

**Admin** — [`ResultsPage`](../src/pages/admin/ResultsPage.tsx) aggregates per
candidate: aptitude and coding attempts, latest of each, code submissions,
overall status (`PASSED` / `FAILED` / `PARTIAL`).
[`CandidateResultDetailPage`](../src/pages/admin/CandidateResultDetailPage.tsx)
drills in, using
[`BandCards`](../src/components/admin/result/BandCards.tsx),
[`TestCaseCard`](../src/components/admin/result/TestCaseCard.tsx),
[`CodeBlock`](../src/components/admin/result/CodeBlock.tsx),
[`ProctoringCaptures`](../src/components/admin/result/ProctoringCaptures.tsx) and
[`AssessmentStanding`](../src/components/admin/AssessmentStanding.tsx).

**Candidate** — [`ResultsListPage`](../src/pages/candidate/ResultsListPage.tsx)
and [`ResultDetailPage`](../src/pages/candidate/ResultDetailPage.tsx). Both sides
compute through [`result.utils.ts`](../src/utils/result.utils.ts), so admin and
candidate always quote identical numbers.

**Reads**

| Endpoint | Permission |
| --- | --- |
| `GET /api/get-results?email=&jobPrefix=` | authenticated |
| `GET /api/get-results-by-job-prefix?jobPrefix=` | `JOB_APPLICATION_READ_ALL` |
| `GET /api/get-results-by-id/{id}` | authenticated |
| `GET /api/compiler/results/code` | `COMPILER_RESULTS_READ` |
| `GET /api/compiler/results/by-job-prefix` | `COMPILER_RESULTS_READ` |

**Exports**

- Excel via [`results-export.utils.ts`](../src/utils/results-export.utils.ts) —
  ExcelJS dynamically imported so it stays out of the candidate bundle; cells
  carry typed numbers and dates, not display strings, so a recruiter can sort and
  average. Includes a final summary sheet with per-candidate performance metrics
  (commit `e8d8111`).
- PDF answer sheets via
  [`answer-sheet.utils.ts`](../src/utils/answer-sheet.utils.ts) and
  [`AnswerSheetExportDialog`](../src/components/admin/result/AnswerSheetExportDialog.tsx).
- Question-paper export via
  [`QuestionPaperExportDialog`](../src/components/admin/QuestionPaperExportDialog.tsx).

**Colour rule** — [`scoreColor()`](../src/utils/result.utils.ts) lets a recorded
verdict win over the 80/60 heuristic bands. Without that, a module that PASSED on
45% was drawn red beside its own green PASSED badge.
